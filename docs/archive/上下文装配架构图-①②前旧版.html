上下文是怎么装配出来的

deepseek-code · 架构图 + 判据 + 实测数据 · 所有数字来自 npm run context:audit（探针观测真实内核外发请求，非估算）

一句话结论：一次任务里模型看到的东西 = 6K 固定税 + 一路只增不减的历史。固定税里有一份纯重复（1K 人肉工具清单），历史里 84% 是一条 read_file 的全文——它在之后每一步被重复投递，任务 6 步就重复 6.6 倍。该压的只有一处，该删的只有一处，而且它们都不是同一件事。

教学点 · 成本的正确单位不是「字节」，是「字节 × 剩余步数」。同一句 32K 的文件内容，在第 1 步读入只需再送 2 次；如果它在第 1 步之前就被塞进 prompt，就要送 3 次。所以上下文优化的杠杆不在「少说一句话」，而在晚点取、取完早退场。

三 · 失败任务的形状（你那次五子棋空转）

同一编辑重复 4 次 → 被 detectCycle 抓住，repeat_loop 退出（步数 4）。把参数每次改一点骗过周期检测 → 走到 no_progress，此时多出一栏，值得细看：

步16.1K 固定 99.2%
步46.8K 固定 88.8%
步54.6K 固定 72.4%
内核一次性反馈 0.3K工具 schema 2.7K步 5 该段消失 = 收尾轮主动撤掉工具（实测 -2.7K），模型结构上无法再调用

这里有两个此前只靠推理、现在有数的事实：

① 「按情况裁剪注入」在仓库里已有一处正确示范——forceNoTools 收尾轮把工具 schema 整个摘掉（实测 −2.7K）。它不是为了省钱，是为了让模型结构上无法再调工具。这才是针对性注入该有的样子：裁剪的是能力，不是措辞。

② 那条 0.3K 的一次性反馈是正确性问题，不是容量问题。它说「不要再尝试任何操作」——只对那一步有效，却永久留在 this.messages 里。你换话题之后、第十轮之后，模型每步仍读到这句。省它 0.3K 毫无意义，删它的时机才是重点。

四 · 优质上下文的定义与判据

定义（唯一必须记住的一条）：LLM 是纯函数，一串 token 进 → 一串 token 出。「上下文」就是这一次调用输入字符串的全部内容，没有别的地方可藏信息。于是失败模式只有两种，你以后所有诊断都会归到这两类：

缺席该进去的事实没进去 → 模型只能猜 → 幻觉就是这么来的
失察进去了但没被用上 → 位置/长度/噪声稀释导致

推论：在 prompt 里写「不要凭记忆猜测、必须诚实」是治症状。缺席就补事实，失察就调位置/减噪声。分不出这两种，调上下文就是瞎调。

五条判据（可逐条验，且必须绑在「某一步的某次决策」上才成立）

#判据怎么验（证伪方法）本次实测

关于判据 4 的诚实记录：我上一轮凭结构推理断言「工具段插在准则中间会破坏前缀缓存对齐」。探针实测：同一会话内 system 逐字节不变（4 个场景全部只出现 1 个 sha 版本），缓存命中，该断言错误。真实风险只在跨会话（工作空间路径一变前缀就换）。这就是判据该有的用法：能证伪，不能一次证成。

你的类比需要换掉。「证正方形」隐含承诺存在确定性证明——上下文没有这东西。模型是随机的，同一份上下文两次跑出不同行为，你无法证明它「足够好」，只能在 N 次里以某置信度检验它「够用」。可用的类比不是几何，是测量学：定义判据 → 设计可操作实验（删一段/挪位置看行为变不变）→ 跑多次统计。没有这一步转换，你会一直在理论层原地打转。

五 · 处置矩阵：压 / 删 / 省 / 不动

「处理上下文」在物理上只有三种操作：原样保留、删除、改写。任何其他说法都是它们的组合。所以每个桶都必须回答：做哪种？失真什么？失真了怎么找回？

处置桶实测体量依据（哪条轴决定）
不动
保留		人格准则 + 环境段 + 工具 schema5.0K / 步可再生性=派生但成本极低；挥发度低 → 实测前缀逐字节稳定，动了反而砸掉 prompt cache
省
去重		system 内的人肉工具清单1.0K / 步权威版本已在 tools 字段（2.7K，协议必付）；两份并存属判据 2 的噪声。改动前须先解「仅以下工具存在」的构造性保证
删
TTL		内核一次性反馈0.3K挥发度=单步。省字节是次要的，理由是正确性：过期指令留在历史里会继续约束模型
压
降详		历史:工具结果（可重跑）32.3K / 84%可再生性=重跑一次即得 → 引用化而非复述化：留「曾调 read_file(src/big.ts) 返回 301 行，已折叠」，让模型自己决定要不要换回细节
禁压用户消息 · 一次性写类结果 · 模型结论0.5K不可再生；且模型结论是 D 级未验证内容，摘要成 S 级断言即污染

引用化 vs 复述化——这条是压缩设计里最容易做错的一处。把旧工具结果摘要成一段话，摘要一旦写错，模型就基于假事实行动，比直接截断更糟（截断至少让模型知道信息缺失）。留指针则不失真：模型知道细节存在、在哪、换回它要花多少。压缩的安全边界是「不新增断言」。

并且：模型视图与用户视图必须是两份东西。压缩只作用于发给模型的上下文，绝不作用于用户可审计的记录——原文永远在 trace / session 里，TUI 的 Ctrl+O 折叠层就是现成的找回入口。这条边界是 step 3 顺手建好的，现在是它回报的时候：有了它，模型侧才敢激进降详。

六 · 还缺的三块地基

主动预算闸门
缺
hub.actorContextWindow() 存在但内核从不调用；usage.inputTokens 累加了却不与 128K 比较 → 没有确定的「该压了」触发条件，token_limit 只能被动等服务商报错
指纹一致性
冲突
detectCycle 依赖完整工具结果与稳定 args 才抓得住地转；把结果压成头几行会让刚修好的反空转保护重新失明。两者必须共用一套结果指纹
可检视性
半成品
ledger 已落元数据（逐条 role 字节数），开 DSA_OUTBOUND_DEBUG=1 才落正文。缺的是一个 /context 视图——看不出模型看到了什么，就永远分不清「它笨」还是「上下文违约」

七 · 怎么自己跑一遍

npm run context:audit # 默认场景
npx tsx scripts/context-audit.ts --scenario all
npx tsx scripts/context-audit.ts --scenario varying-failures --pretty
DSA_OUTBOUND_DEBUG=1 npm start # 真任务：落完整出机正文
cat ~/.dsa/outbound/$(date +%Y-%m).jsonl # 每次调用的逐条 role 字节

四个场景：explore-then-fix（大文件绑架）· failures（周期拦截）· varying-failures（一次性反馈堆积）· long-run（比例演变）

建议的动手顺序（代价从小到大，每步都能用同一个探针当场验收）

① 一次性反馈加 TTL（纯正确性）→ 看「内核反馈」栏在末步归零 ② system 工具清单去重（1.0K）→ 看首步固定税从 6.0K 降到 5.0K ③ 可重跑工具结果降详 + contextWindowOf 预算闸门 → 看那条增长曲线从 83% 压下去。①② 不改任何决策行为，是可回退的结构性改动；③ 才真正碰到模型的判断，必须在有 ①② 的干净基线上做。

探针实现：scripts/context-audit.ts · 挂载点 provider.serialize()（hub 唯一外发路径的结构化末梢，挂别处都可能漏）
token 为估算（CJK≈1 字/token、ASCII≈4 字/token），字节数为精确值 · 生成于 2026-09-21
