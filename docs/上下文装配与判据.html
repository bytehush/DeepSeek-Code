上下文是怎么装配出来的

deepseek-code · 架构图 + 判据 + 实测数据 · 所有数字来自 npm run context:audit（探针观测真实内核外发请求，非估算）

一句话结论（本页数字为 ①②③ 全部落地后同日复测）：一次任务里模型看到的东西 = 5.1K 固定开销 + 历史，但历史不再是无损累加。
三处都已改掉：① 一次性内核反馈改住 pendingSystem——装配下一步请求时取出即清空，过期指令不再留在历史里；② system 里那份人肉工具清单整段删除，工具描述的唯一来源改成请求的 tools 字段，每步固定开销 6.0K → 5.1K；③ 已被后来的成功写入否证的 read 结果，在发给模型的那一份里降详成引用——同一条任务的末步从 37.6K 降到 5.7K（省 32.1K），那条 32.3K 的橙条只剩 0.2K。
首步占比依旧 98.6%~99.1%——固定开销从来不是主要矛盾，主要矛盾（一条大 read 结果全程重投）现在被③按「与事实矛盾才折」的规则拆掉了。重复投递倍数（累计 ÷ 峰值步）3 步任务 1.3 次、5 步失败任务 4.4 次。

三 · 失败任务的形状（你那次五子棋空转）

同一编辑重复 4 次 → 被 detectCycle 抓住，repeat_loop 退出（步数 4）。把参数每次改一点骗过周期检测 → 走到 no_progress，此时多出一栏，值得细看：

步15.1K 固定 99.1%
步45.9K 固定 87.1%
步53.7K 固定 65.6%
内核一次性反馈 0.3K工具 schema 2.7K步 5 该段消失 = 收尾轮主动撤掉工具（实测 -2.7K），模型结构上无法再调用

这里有两个此前只靠推理、现在有数的事实：

① 「按情况裁剪注入」在仓库里已有一处正确示范——forceNoTools 收尾轮把工具 schema 整个摘掉（实测 −2.7K）。它不是为了省钱，是为了让模型结构上无法再调工具。这才是针对性注入该有的样子：裁剪的是能力，不是措辞。

② 那条 0.3K 的一次性反馈是正确性问题，不是容量问题——这条判断已经落成代码。它说「不要再尝试任何操作」，只对被打断的那一步有效；修复前它被 push 进 this.messages，于是你换话题之后、第十轮之后，模型每步仍读到这句。现在它住在 pendingSystem 里，装配下一步请求时取出即清空。省那 0.3K 毫无意义（末步占比 7.3%），改它的时机才是重点：这是本页唯一一处「字节最少、优先级最高」的修复。

四 · 优质上下文的定义与判据

定义（唯一必须记住的一条）：LLM 是纯函数，一串 token 进 → 一串 token 出。「上下文」就是这一次调用输入字符串的全部内容，没有别的地方可藏信息。于是失败模式只有两种，你以后所有诊断都会归到这两类：

缺席该进去的事实没进去 → 模型只能猜 → 幻觉就是这么来的
失察进去了但没被用上 → 位置/长度/噪声稀释导致

推论：在 prompt 里写「不要凭记忆猜测、必须诚实」是治症状。缺席就补事实，失察就调位置/减噪声。分不出这两种，调上下文就是瞎调。

五条判据（可逐条验，且必须绑在「某一步的某次决策」上才成立）

关于判据 4 的诚实记录：我上一轮凭结构推理断言「工具段插在准则中间会破坏前缀缓存对齐」。探针实测：同一会话内 system 逐字节不变（4 个场景全部只出现 1 个 sha 版本），缓存命中，该断言错误。真实风险只在跨会话（工作空间路径一变前缀就换）。这就是判据该有的用法：能证伪，不能一次证成。

你的类比需要换掉。「证正方形」隐含承诺存在确定性证明——上下文没有这东西。模型是随机的，同一份上下文两次跑出不同行为，你无法证明它「足够好」，只能在 N 次里以某置信度检验它「够用」。可用的类比不是几何，是测量学：定义判据 → 设计可操作实验（删一段/挪位置看行为变不变）→ 跑多次统计。没有这一步转换，你会一直在理论层原地打转。

五 · 处置矩阵：压 / 删 / 省 / 不动

「处理上下文」在物理上只有三种操作：原样保留、删除、改写。任何其他说法都是它们的组合。所以每个桶都必须回答：做哪种？失真什么？失真了怎么找回？

处置桶实测体量依据（哪条轴决定）
不动
保留		人格准则 + 环境段 + 工具 schema5.1K / 步可再生性=派生但成本极低；挥发度低 → 实测前缀逐字节稳定，动了反而砸掉 prompt cache
省 已做②system 内的人肉工具清单1.0K / 步 → 0权威版本已在 tools 字段（2.7K，协议必付），两份并存属判据 2 的噪声。我原以为删它会丢掉「仅以下工具存在」的构造性保证——方向恰好反了：tools 字段是服务商硬约束（只有列出的名字能被调），自然语言清单只是软提示，而且已经和 schema 描述漂移过。删副本才是更强的保证，回归断言已改钉在 wireSpecs() 上
删 已做①内核一次性反馈0.3K → 不入历史挥发度=单步。省字节是次要的，理由是正确性：过期指令留在历史里会继续约束模型。现在只拼进下一步请求，消费即弃；clear()、换回合、从 session 恢复时一并作废
压
已做③		历史:工具结果（可重跑）32.3K / 86.0% → 0.2K触发条件不是「太长」也不是「太旧」，是「已与后来的事实矛盾」：这条读结果之后若有一次对同一路径的成功写入，它描述的状态就不成立了——折它同时省字节和去掉判据 3 的矛盾（旧读结果与新写结果并存，模型只能猜哪个算数）。第二条独立触发是窗口压力（估算输入 > 60%）。产物是引用化而非复述化：只说调了哪个工具、多少行/字节、被谁取代、怎么取回，不摘要内容，让模型自己决定要不要换回细节
禁压用户消息 · 一次性写类结果 · 模型结论0.4K不可再生；且模型结论是 D 级未验证内容，摘要成 S 级断言即污染

引用化 vs 复述化——这条是压缩设计里最容易做错的一处。把旧工具结果摘要成一段话，摘要一旦写错，模型就基于假事实行动，比直接截断更糟（截断至少让模型知道信息缺失）。留指针则不失真：模型知道细节存在、在哪、换回它要花多少。压缩的安全边界是「不新增断言」。

并且：模型视图与用户视图必须是两份东西。压缩只作用于发给模型的上下文，绝不作用于用户可审计的记录——原文永远在 trace / session 里，TUI 的 Ctrl+O 折叠层就是现成的找回入口。这条边界是 step 3 顺手建好的，现在是它回报的时候：有了它，模型侧才敢激进降详。

③ 实际发出的引用（样例由 fitContext() 现场跑出的原文，不是手写示意）：

（历史工具结果已降详：read_file {"path":"src/big.ts"} 曾返回 201 行 / 4600 字节。此后对同一路径有成功写入，这份内容描述的状态已过时。原文未删除；需要其中内容请重新调用 read_file 取回。）

四个场景：explore-then-fix（大文件绑架）· failures（周期拦截）· varying-failures（一次性反馈堆积）· long-run（比例演变）

动手顺序（代价从小到大，每步都能用同一个探针当场验收）

① 已做一次性反馈消费即弃 → 验收：「内核反馈」栏只出现在收尾轮（末步 0.3K / 7.3%），且 kernel.history 里一条 system 都没有。

② 已做system 工具清单去重 → 验收：每步固定开销 6.0K → 5.1K（-15%）；wireSpecs() 成为工具描述唯一事实源，promptSection() 整个方法删除，防幽灵工具的断言改钉在 tools 字段上。

③ 已做可重跑读类结果引用化降详 + hub.actorContextWindow() 预算闸门 → 验收：那条 86.0% 的橙条压到 0.7%（32.3K → 0.2K），失败与被拒结果原文不动（ToolOutcome 结构性豁免，不按文案猜），eval 仍 15/15。①② 不改任何决策行为，是可回退的结构性改动；③ 才真正碰到模型的判断，所以必须踩在 ①② 的干净基线上做。

① 的字节收益只有 0.3K，却排第一个做：按字节数排优先级，会把正确性排到最后——这是上下文工程里最常见的排序错误。
